## 2. 신규 발견 사항

### [RT-7 · 높음] RT-4 수정안의 "즉시 세션 무효화"가 리프레시 토큰 경로로 우회됨 — 2FA 강제 실효 없음

- **위치**: 작업지시서 WP-5 작업 항목 9, WP-2 작업 항목 3(AUTH-3)
- **결함**: WP-5-9는 TOTP 미등록자에게 `OPERATOR` 이상을 부여하면 "즉시 `perm_version` 증가로 기존 세션을 무효화하여 재로그인을 강제"한다고 한다. 그러나 pv 증가는 **Access Token만** 거부시킨다. 대상자의 클라이언트는 유효한 Refresh Token으로 `/auth/refresh`를 호출하고, AUTH-3의 검사 항목은 `status=ACTIVE` 재검증뿐이므로 **새 pv가 반영된 새 Access Token이 TOTP 등록 없이 발급**된다. 재로그인은 발생하지 않고, "다음 로그인까지의 창"을 없애려던 수정이 사실상 무효가 된다.
- **실패 시나리오**: TOTP 미등록 회원 B에게 `OPERATOR` 부여 → B의 앱이 자동 토큰 갱신 → B는 2FA 없이 회원 정지·역할 부여 등 관리 행위 지속.
- **v3 반영 지시** (택일 또는 병행, 구조적 해법으로):
  - (a) `OPERATOR` 이상 부여 시 pv 증가와 **함께 대상자의 refresh family 전체 폐기** — 재로그인이 물리적으로 강제됨. (정지 처리 MEM-4와 동일 패턴이므로 구현 일관성도 좋음)
  - (b) AUTH-3(토큰 갱신)에 "2FA 요구 대상(관리 역할 보유)인데 TOTP 미등록이면 갱신 거부" 검사 추가.
  - 권고: (a)를 기본으로 하고, (b)를 방어 심층(defense in depth)으로 병행. WP-5 DoD의 실증 항목을 "부여 직후 **Refresh Token 갱신 시도까지 포함하여** 관리 API 접근이 불가"로 강화할 것.

### [RT-8 · 중간] 최초 `SUPER_ADMIN` "활성화" 조건과 로그인 거부 규칙의 순환 모순 (문서 모호성)

- **위치**: 작업지시서 WP-1 작업 항목 2("완료해야 계정 활성화"), WP-2 작업 항목 2(AUTH-2: `status≠ACTIVE` 로그인 거부)
- **결함**: WP-1은 "최초 로그인 시 비밀번호 변경+TOTP 등록을 완료해야 **계정 활성화**"라 쓰고, AUTH-2는 `status≠ACTIVE`면 로그인 자체를 거부한다. 문면대로면 활성화 전엔 로그인 불가, 로그인해야 활성화 가능 — 순환이다. 구현자가 임의 해석(예: 예외적 로그인 허용 코드)을 넣으면 그것이 곧 땜질이 된다.
- **v3 반영 지시**: 상태와 온보딩 플래그를 분리해 명문화하라 — 시드 계정은 `status=ACTIVE`로 생성하되 `must_change_password`·`totp_enrollment_required` 플래그를 두고, **이 플래그가 남아 있는 동안 세션 발급 범위를 온보딩 API(비밀번호 변경·TOTP 등록)로만 제한**한다. "계정 활성화"라는 표현을 "온보딩 완료 전 일반·관리 API 접근 불가"로 교체. (이 방식은 WP-5-9의 재로그인 TOTP 강제 흐름과 동일 메커니즘으로 통일 가능)

### [RT-9 · 낮음] WP-6b와 WP-5의 주차 배분 모순 — RT-6-3과 동일 유형 재발

- **위치**: §2 주차 배분("4주차 WP-5·WP-6b") vs WP-5 착수 조건("WP-6b 완료")
- **결함**: WP-4에서 고친 것과 같은 유형의 모순이 WP-6b에 남아 있다. WP-6b는 WP-5 착수 전 완료여야 하는데 같은 4주차에 병행 표기되어 있다. WP-6b의 착수 조건(WP-6a 완료)은 2주차 초에 이미 충족되므로 앞당길 수 있다.
- **v3 반영 지시**: WP-6b를 3주차(WP-3 마무리와 병행)로 이동하거나, "4주차 초 WP-6b 완료 후 WP-5 착수"로 표기 정정.

### [RT-10 · 낮음] 정합성 3건

1. **부트스트랩 예외 범위 초과**: §5-4는 "최초 커밋(2207f39)"만을 1회성 예외로 기술했는데, v2 반영 커밋(f563a34)도 브랜치 보호 설정 전 `main`에 직접 push되었다. 현재 문면상 f563a34는 스스로 정한 규칙의 미기록 위반이 된다. 예외 기술을 "브랜치 보호 가동(WP-0) 이전의 문서 부트스트랩 구간 커밋"으로 정정하고 해당 커밋 해시를 열거할 것. 이후 문서 커밋도 보호 가동 전이라면 동일하게 열거에 추가.
2. **기획서 §16.3-1과 break-glass의 상호 참조 누락**: §16.3-1("운영 DB 직접 수정 금지")에 승인된 예외(§10.1 break-glass)가 생겼으므로, §16.3-1에 "유일한 예외는 §10.1의 break-glass 절차"를 명기해야 두 조항이 모순으로 읽히지 않는다. (기획서 v1.5 또는 차기 개정에 반영)
3. **쿼럼 구조의 성립 조건 미명시**: §9.5의 쿼럼("발의자 외 활성 `SUPER_ADMIN` 과반수, 최소 2인")은 전체 `SUPER_ADMIN`이 3인 이상일 때만 성립한다. 흔한 운영 형태인 2인 체제에서는 쿼럼 경로가 원천 불성립하여 break-glass만 남는다. Phase 3 설계 시 혼선이 없도록 "3인 미만 체제에서는 쿼럼 불성립 → break-glass"를 §9.5에 한 줄 명시할 것.
