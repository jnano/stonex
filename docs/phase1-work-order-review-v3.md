## 2. 신규 발견 사항

### [RT-11 · 중간] "OPERATOR 이상"이라는 판정 기준이 정의 불가 — rank 제거(v1.2) 때 정리되지 못한 기획서 잔재

- **위치**: 기획서 §10.4("관리 역할(`OPERATOR` 이상) 계정은 2FA 강제"), 작업지시서 WP-2 항목 3(AUTH-3: "관리 역할 보유" 판정), WP-5 항목 9("`OPERATOR` 이상 역할 부여 시")
- **결함**: 기획서 v1.2에서 rank(서열 숫자)를 제거하고 INV-2로 "서열 필드의 보안 규칙 사용 금지"를 못박았다. 그런데 §10.4의 "`OPERATOR` **이상**"이라는 서수 표현이 그대로 남았고, 작업지시서의 RT-7 반영(AUTH-3 갱신 거부)이 이 미정의 술어("관리 역할 보유")를 보안 검사 조건으로 사용하게 되었다. **현재 체계에는 "이상"을 판정할 근거가 없다** — `display_order`로 판정하면 INV-2 위반(G-2에 걸림)이고, 구현자가 임의 목록을 하드코딩하면 새 역할 추가 시 2FA가 조용히 누락되는 확장성 구멍이 된다.
- **책임 소재의 명시**: 이는 작업팀의 잘못이 아니라 **기획서 v1.2 개정 시 rank 제거의 파장을 §10.4까지 추적하지 못한 기획서 작성자(레드팀 본인)의 잔재 결함**이다. 작업팀의 RT-7 반영이 이 잔재를 보안 검사의 필수 술어로 끌어올리면서 표면화되었다.
- **해소 지시** (기획서 v1.6 + 작업지시서 v4, **WP-2 착수 전 완료 필수** — AUTH-3 갱신 거부 검사가 이 술어를 요구하므로):
  - 기획서 §5.2 `roles`에 `requires_2fa BOOLEAN NOT NULL DEFAULT false` 속성을 추가하고, §10.4를 "**`requires_2fa=true` 역할을 하나라도 보유한 계정은 2FA를 강제한다**"로 재정의한다. 시드에서 `OPERATOR`·`SUPER_ADMIN`에 true 지정.
  - 근거: 판정이 데이터에서 파생되고(INV-2 정합), 새 역할 생성 시 명시적으로 선택하게 되어 조용한 누락이 없으며, 역할 생성 UI(ADM-2)에서 이 플래그 변경을 `admin.role.manage` + 감사 기록으로 통제할 수 있다. "민감 Permission 보유 여부"로 파생하는 대안도 검토했으나, 민감 목록이라는 별도 관리 대상을 만들어 오히려 정의 지점이 늘어나므로 역할 속성 방식을 권고한다.
  - 작업지시서 v4: WP-1 시드에 `requires_2fa` 반영, WP-2 AUTH-3·WP-5-9의 "관리 역할" 표현을 "`requires_2fa` 역할 보유"로 교체, G-4 시드 정합성 검사에 "OPERATOR·SUPER_ADMIN의 requires_2fa=true" 확인 추가.

### [RT-12 · 낮음] 온보딩 플래그가 기획서 §5.2 `users` DDL에 없음 — "기획서 우선" 원칙상 구현 근거 부재

- **위치**: 작업지시서 WP-1 항목 2·WP-2 항목 7(`must_change_password`, `totp_enrollment_required`), 기획서 §5.2 `users`
- **결함**: RT-8 해소로 도입된 두 온보딩 플래그가 기획서 DDL에는 존재하지 않는다. 작업지시서 표두가 "충돌 시 기획서 우선"을 선언하므로, 문면대로면 구현자는 이 컬럼을 만들 근거가 없다.
- **해소 지시** (기획서 v1.6, WP-1 착수 전): §5.2 `users`에 두 플래그 컬럼(BOOLEAN NOT NULL DEFAULT false)을 추가하고, §8(인증) 절에 온보딩 게이트 문단(플래그 존속 중 세션 접근 범위 제한, 해소 메커니즘)을 1개 신설하여 작업지시서 WP-2-7의 규칙에 기획서상 근거를 부여한다. TOTP 시크릿 저장 컬럼(암호화 보관)도 이때 함께 정의할 것.

## 3. 판정과 후속 절차

1. **작업지시서 v3는 승인한다.** WP-0·WP-1 착수 가능.
2. **RT-11 해소(기획서 v1.6 + 작업지시서 v4)는 WP-2 착수 전 완료가 필수 조건**이다. RT-12는 같은 개정에 병합한다(WP-1의 Prisma 스키마 작성 전 반영이 이상적).
3. v4는 RT-11·RT-12 반영 내역 확인의 **서면 확인만으로 승인 처리**한다. 단, 반영 과정에서 보안 검사 로직이 새로 추가·변경되는 경우에만 재검수를 다시 연다.
4. 3차에 걸친 검수에서 지적 유형이 "구조 결함 → 수정안의 우회 경로 → 잔재 정의 공백"으로 수렴하고 있음은 문서 체계가 안정화되고 있다는 신호다. v4 이후 추가 개정은 구현 중 발견 사항 기반으로 전환한다.
