## 1. 목적과 범위

### 1.1 목적

기획서 §12 Phase 1("기반")을 실행 가능한 작업 패키지(Work Package, WP) 단위로 분해하고, 각 작업의 착수 조건·작업 항목·완료 조건·산출물·의존 관계를 정의한다. 구현 담당자는 본 문서의 WP 단위로 작업을 수령하고, 완료 조건 충족 여부로 검수받는다.

### 1.2 범위

- **포함**: WP-0 ~ WP-8 (저장소 기반 → 스키마 → 감사 기록 함수(WP-6a) → 인증 → 평가기 → 캐시 → 감사 로그 운영·break-glass 런북(WP-6b) → 회원 관리 → 관리자 콘솔 → 통합 검증)
- **제외**: 파일·도메인 리소스 기능(Phase 2), 런타임 불변식 순찰 워커(Phase 2), §9의 선택 확장 전부(Phase 3). **`SUPER_ADMIN` 쿼럼 승인 구조(기획서 §9.5)도 Phase 3 확장으로 본 작업지시서 범위에서 명시적으로 제외한다** — Phase 1의 `SUPER_ADMIN` 비상 회수는 break-glass 런북(WP-6)으로만 대응한다(발주자 결정, 기획서 §10.1)
- 단, `resource_grants` **테이블과 평가기 4단계(Grant 평가) 로직은 Phase 1 범위에 포함**한다(기획서 §4.1 — "계층 3은 Phase 1에서 테이블과 평가 로직까지 구현"). Phase 1에서는 이 경로를 사용하는 기능이 없으므로 단위 테스트로만 검증한다.

### 1.3 전 작업 공통 준수 사항

1. 기획서 §1.4의 불변 규칙 INV-1 ~ INV-7을 모든 코드에 적용한다. 코드 리뷰 체크리스트의 최상단 항목이다.
2. 커밋 규약: Conventional Commits. **권한 모델(permissions·roles·매핑·매트릭스)을 변경하는 커밋은 `perm:` 타입 필수**(기획서 §16.3-3).
3. `main` 직접 push 금지. 모든 변경은 PR + 리뷰 승인으로만 병합한다(WP-0에서 브랜치 보호로 강제).
4. 언어는 TypeScript 단일. 거버넌스·스크립트 포함 예외 없음(기획서 §15.1).

## 2. 작업 패키지 개요와 의존 관계

WP-6(감사 로그)은 두 부분으로 분할한다(RT-2 반영): **WP-6a** 트랜잭션 내 감사 기록 함수(핵심 — WP-2의 선행 조건), **WP-6b** 파티션 운영·append-only DB 권한·break-glass 런북(WP-5 착수 전 완료).

        │
        ▼
WP-1 DB 스키마·시드
        │
        ├──────────────┬────────────────┐
        ▼              ▼                ▼
WP-6a 감사 기록    WP-3 권한 평가기   WP-6b 감사 로그 운영
  함수 (핵심)          │              + break-glass 런북
        │              │              (WP-5 착수 전 완료)
        ▼              │                │
WP-2 인증              │                │
        │              │                │
        └────┬─────────┘                │
             ▼                          │
       WP-4 권한 스냅샷 캐시             │
             │                          │
             ▼                          │
       WP-5 회원 관리 ◄─────────────────┘
             │
             ▼
       WP-7 관리자 콘솔 (ADM-1~3)
             │
             ▼
       WP-8 통합 검증·완료 판정

- WP-3은 WP-1 완료 후 착수한다. WP-2는 WP-1 **및 WP-6a** 완료 후 착수한다(AUTH-1의 `MEMBER` 자동 부여가 감사 기록을 요구 — RT-2). WP-2와 WP-3은 서로 독립이므로 병행 가능하다.
- CI 게이트는 준비된 것부터 단계 가동한다(RT-3 반영): WP-0에서 G-2, WP-1에서 G-4, WP-3에서 G-5, WP-8에서 G-1·G-3. 상세는 각 WP 참조.
- 주차 배분(6주 기준): 1주차 WP-0·WP-1 / 1주차 말~2주차 초 WP-6a / 2주차 WP-2·WP-3 / **3주차 WP-3 마무리·WP-6b**(RT-9 — WP-6b 착수 조건은 2주차 초에 충족되므로 앞당김), **3주차 후반**(WP-2·WP-3 완료 후) WP-4 착수 / 4주차 WP-5(WP-6b 기완료 상태에서 착수) / 5주차 WP-7 / 6주차 WP-8 + 버퍼. (RT-6-3·RT-9: 각 WP는 착수 조건 충족 후에만 착수)

### WP-2. 인증 (AUTH-1~4)

| 항목 | 내용 |
|---|---|
| 참조 | 기획서 §6.1, §8.1, §8.2, §10.4 |
| 착수 조건 | WP-1 완료 **+ WP-6a(트랜잭션 내 감사 기록 함수) 완료** (RT-2) |
| 의존 | WP-1, WP-6a (WP-3과 병행 가능) |

**작업 항목**

1. [AUTH-1] 회원가입: 이메일 인증 완료 시 `status=ACTIVE` 전환 + `MEMBER` 역할 자동 부여. **역할 자동 부여는 권한 변경이므로 WP-6a의 감사 기록 함수를 사용해 동일 트랜잭션에서 기록한다(INV-6, RT-2).** 이메일 발송은 인터페이스로 추상화하고 개발 환경에서는 콘솔/로컬 어댑터 사용(발송 수단은 기획서 §13.2 미결 — 결정 시 어댑터 교체만으로 대응).
2. [AUTH-2] 로그인: argon2id 검증, 실패 5회 시 15분 잠금, `status≠ACTIVE` 거부. 유출 비밀번호 대조(HIBP k-anonymity)·최소 10자 정책.
3. [AUTH-3] 토큰 갱신: Refresh Token 회전, 재사용 탐지 시 family 전체 폐기, **갱신 시점 `status=ACTIVE` 재검증**(불통과 시 갱신 거부 + family 폐기). **추가 검사(RT-7-b, 방어 심층)**: 갱신 시점에 대상자가 2FA 요구 대상(관리 역할 보유)인데 TOTP 미등록이면 갱신을 거부한다 — 갱신 경로가 2FA 강제(WP-5-9)를 우회하는 것을 차단.
4. [AUTH-4] 비밀번호 재설정: 재설정 시 전체 refresh family 폐기.
5. 토큰 구조(기획서 §8.1 그대로): Access JWT 10분, 페이로드 `sub`·`tenant`·`pv`·`exp`만 — **역할·권한 목록 JWT 포함 금지**. Refresh는 불투명 랜덤, DB에 SHA-256 해시만 저장, 14일.
6. 인증 API 속도 제한: 5회/분/IP.
7. 2FA(TOTP)와 온보딩 게이트: 관리 역할 강제는 역할 부여 기능(WP-5)과 맞물리므로, **본 WP에서는 TOTP 등록·검증 모듈과 온보딩 게이트를 구현**하고 "OPERATOR 이상 강제" 연동은 WP-5에서 활성화. **온보딩 게이트(RT-8)**: `must_change_password` 또는 `totp_enrollment_required` 플래그가 켜진 계정은 로그인은 가능하되(`status=ACTIVE`), 발급되는 세션의 접근 범위가 **온보딩 API(비밀번호 변경·TOTP 등록)로만 제한**된다 — 두 플래그를 모두 해제해야 일반·관리 API 접근이 열린다. 최초 `SUPER_ADMIN`(WP-1 시드)과 WP-5-9의 재로그인 TOTP 강제가 **동일한 이 게이트 메커니즘**을 사용한다.

**완료 조건 (DoD)**

- [ ] AUTH-1~4 통합 테스트 통과 (정상 흐름 + 잠금·재사용 탐지·정지 계정 갱신 거부의 이상 흐름)
- [ ] 가입 시 `MEMBER` 역할 부여가 감사 로그에 기록되고, 감사 기록 실패 주입 시 가입 트랜잭션이 롤백됨을 실증 (RT-2)
- [ ] 최초 `SUPER_ADMIN`이 온보딩(비밀번호 변경+TOTP 등록) 완료 전에는 온보딩 API 외 어떤 일반·관리 API도 호출 불가하고, 완료 후 정상 접근됨을 실증 (RT-4·RT-8)
- [ ] 관리 역할 보유+TOTP 미등록 상태의 Refresh Token 갱신 시도가 거부됨을 실증 (RT-7-b)
- [ ] 폐기된 Refresh Token 재사용 시 family 전체가 즉시 무효화됨을 테스트로 실증
- [ ] JWT 페이로드에 역할·권한이 없음을 테스트로 고정 (회귀 방지)

**산출물**: 인증 모듈, 토큰 서비스, 속도 제한 미들웨어, TOTP 모듈, 통합 테스트

| 항목 | 내용 |

| 참조 | 기획서 §4.3, §4.6, §4.7, §4.8, §7.3, §7.4 |
| 착수 조건 | WP-1 완료 |
| 의존 | WP-1 (WP-2와 병행 가능) |

**작업 항목**

1. `AuthorizationService.can(subject, permission, resource?)` — 기획서 §4.7의 5단계(0~5)를 **순서 그대로** 구현:
   - 0단계 주체 상태 → 1단계 리소스 상태 게이트 → 2단계 명시적 DENY Grant → 3단계 역할 기반(scope 해석: global 즉시 / owned는 `owner_id` 일치 시) → 4단계 ALLOW Grant(만료 검사 포함) → 5단계 Default Deny.
   - 리소스 상태 집합: file `{ACTIVE}`, domain `{UNVERIFIED, VERIFIED}` + 조회 한정 `{SUSPENDED}` (기획서 §4.7-1).
2. Dominance 모듈(기획서 §4.6):
   - 우위 검사: A 집합 ⊋ B 집합일 때만 관리 행위 허용. 동집합·비교불가 거부. 본인 대상 역할 변경 전면 금지.
   - 부분집합 검사: 역할 R의 집합 ⊆ 부여자 집합일 때만 부여/회수 허용.
   - 판정 결과에 **사유(부족한 Permission 목록)를 구조체로 반환** — 관리 콘솔 표시(§4.6-3)와 향후 시뮬레이터(ADM-5, Phase 2)가 재사용.
3. Guard 체계(기획서 §7.4): `AuthGuard` → `PermissionGuard`(`@RequirePermission` 수집) → `AuthorizationService.can()` → `DominanceGuard`(관리 행위 한정).
4. `@RequirePermission(code, { resource, param })` / `@Public()` 데코레이터. **미선언 엔드포인트는 기동 시점에 서버 기동 실패**(기획서 §7.3). 동일 검사를 CI에서 선행 실행하는 G-5 스크립트 연결.
5. `PolicyService` 뼈대: 관계형 2차 인가(기획서 §7.3)의 표준 위치. Phase 1에서는 회원 관리에 관계 조건이 없으므로 구조와 규약(명명된 정책 함수, 임의 핸들러 구현 금지 — G-2 룰 추가)만 확립.
6. 리소스형 API의 리소스 1회 로드 패턴: 핸들러 진입 전 로드하여 평가기·핸들러 공유(이중 조회 방지, 기획서 §4.7).
7. Semgrep 룰 추가(G-2 2차): 평가기·PolicyService를 우회하는 직접 쿼리 패턴 검출 — 평가기 모듈 경계가 확정된 본 시점에 작성.

**완료 조건 (DoD)**

- [ ] 평가기 표 기반(table-driven) 단위 테스트: 기획서 §4.8 전 사례 8건 + 경계 사례(만료 Grant, DENY 우선, owned·소유자 불일치, 삭제 리소스, 정지 주체 등) 전부 통과
- [ ] Dominance 단위 테스트: 동집합 거부·비교불가 거부·본인 금지·부분집합 부여를 각각 실증
- [ ] `@RequirePermission` 미선언 컨트롤러를 추가하면 서버 기동이 실패하고 CI(G-5)도 실패함을 실증
- [ ] Grant 평가 경로(2·4단계)가 `resource_grants` 수동 삽입 데이터로 단위 테스트 통과 (Phase 1 UI 없음 — §1.2)

**산출물**: `AuthorizationService`, Dominance 모듈, Guard·데코레이터, `PolicyService` 뼈대, G-5 스크립트, Semgrep 룰, 단위 테스트 스위트

### WP-4. 권한 스냅샷 캐시

| 항목 | 내용 |
|---|---|
| 참조 | 기획서 §8.2, §8.3 |
| 착수 조건 | WP-2·WP-3 완료 |
| 의존 | WP-2, WP-3 |

**작업 항목**

1. Redis 스냅샷: 키 `perm:{user_id}`, 값 `{pv, status, roles, permissions:[{code, scope}]}`, TTL 300초. 미적중 시 DB 재구성 + 재기록.
2. 무효화 순서 강제(기획서 §8.3): 권한 변경 트랜잭션에서 (1) `perm_version` 증가 커밋 → (2) Redis 키 삭제. 이 순서를 서비스 계층 공통 함수 하나로 캡슐화하여 개별 기능이 직접 순서를 다루지 않게 한다.
3. pv 대조 체인: 요청 처리 시 JWT `pv` ↔ 스냅샷 `pv` ↔ (불일치 의심 시) DB `perm_version`. JWT pv가 DB와 다르면 Access Token 거부 + 재발급 유도.
4. 역할-권한 매핑 변경 시 보유자 전원 pv 배치 증가 + 키 삭제(`idx_user_roles_role` 사용).
5. 평가기 0단계가 캐시 적중 시에도 `status` 검사를 수행하도록 스냅샷의 `status` 필드 연결.
6. `GET /me`: 프로필 + 권한 스냅샷 반환(프론트 표시 분기용, 기획서 §8.4).

**완료 조건 (DoD)**

- [ ] 통합 테스트: 역할 회수 → 기존 Access Token으로 즉시 재요청 → pv 불일치로 거부됨을 실증 (권한 회수 전파 10초 이내 — 기획서 §11)
- [ ] 역할 매핑 변경 → 보유자 전원의 스냅샷 무효화 실증
- [ ] Redis 장애(중단) 상태에서 DB 폴백으로 요청 처리 지속 실증 (기획서 §11 가용성)

**산출물**: 스냅샷 캐시 모듈, 무효화 공통 함수, `GET /me`, 통합 테스트

### WP-5. 회원 관리 (MEM-1~6)

| 항목 | 내용 |
|---|---|
| 참조 | 기획서 §6.2, §4.6, §7.2, §10.1, §10.2 |
| 착수 조건 | WP-4 완료 + WP-6b 완료 (WP-6a는 WP-2 선행 조건으로 기완료) |
| 의존 | WP-4, WP-6a, WP-6b |

**작업 항목**

1. [MEM-1] 내 프로필 조회/수정 — 본인 판정은 인증 컨텍스트. 이메일 변경 시 재인증.
2. [MEM-2] 회원 목록/상세 — `member.read`. 페이지네이션. 응답 직렬화는 화이트리스트 방식(`password_hash` 등 내부 필드 차단 — 기획서 §10.2).
3. [MEM-3] 회원 수정 — `member.update` + 우위 검사.
4. [MEM-4] 정지/해제 — `member.ban` + 우위 검사. 정지 즉시 pv 증가 + **refresh family 전체 폐기**.
5. [MEM-5] 역할 부여/회수 — `member.role.assign` + 우위 + 부분집합 검사. `expires_at` 임시 역할 지원, 단 `SUPER_ADMIN`은 `expires_at` 지정 불가(기획서 §4.5).
6. [MEM-6] 회원 삭제 — `member.delete` + 우위 검사. 소프트 삭제 + family 폐기 + 해당 사용자가 subject인 Grant 삭제(기획서 §5.3).
7. **최고관리자 보존 불변식**(기획서 §10.1): "활성 `SUPER_ADMIN` ≥ 1"을 회수·정지·삭제 모든 경로에서 사전 검사. 검사~변경을 `SELECT ... FOR UPDATE`로 원자화(동시 강등 경쟁 차단).
8. `SUPER_ADMIN` 부여·회수는 감사 로그에 별도 심각도로 기록(기획서 §4.6-2).
9. 2FA 강제 연동(RT-4·RT-7): `OPERATOR` 이상 역할 부여 시 TOTP 미등록 대상자는 —
   - **부여 즉시** 대상자의 `perm_version` 증가(Access Token 차단) **+ refresh family 전체 폐기(RT-7-a — Access·Refresh 양 경로를 모두 끊어 재로그인을 물리적으로 강제**. 정지 처리 MEM-4와 동일 패턴) + `totp_enrollment_required` 플래그 설정.
   - 재로그인 시 온보딩 게이트(WP-2 항목 7)에 의해 TOTP 등록을 완료해야 일반·관리 API 접근이 열린다.
   - AUTH-3의 갱신 시 TOTP 검사(RT-7-b)가 방어 심층으로 이 규칙을 이중 보증한다.
   "다음 로그인까지" 2FA 없이 관리 행위가 가능한 창을 남기지 않는다.

**완료 조건 (DoD)**

- [ ] MEM-1~6 통합 테스트 통과 (권한별 허용/거부 포함)
- [ ] 우위 검사 통합 테스트: `OPERATOR`가 `SUPER_ADMIN` 정지 시도 → 거부 / 동급 관리자 상호 공격 → 거부 / 본인 역할 변경 → 거부. **주: 동급 거부의 파생으로 탈취된 `SUPER_ADMIN`의 무력화는 시스템 내 정상 경로가 없으며, break-glass 절차(WP-6b 런북)로만 가능하다 — 이는 의도된 동작이다(RT-1, 기획서 §10.1)**
- [ ] `OPERATOR` 이상 부여 직후, 대상자의 기존 Access Token에 의한 관리 API 호출이 즉시 거부되고, **기존 Refresh Token에 의한 갱신 시도까지 거부**되며(RT-7), 재로그인 시 TOTP 등록 완료 전에는 온보딩 API 외 접근이 불가함을 실증 (RT-4·RT-7·RT-8)
- [ ] 마지막 활성 `SUPER_ADMIN` 강등·정지·삭제 시도가 **동시 요청 2건 경쟁 상황에서도** 전부 거부됨을 실증
- [ ] 정지된 계정의 기존 Access Token·Refresh Token이 모두 무효화됨을 실증

**산출물**: 회원 관리 API 일체, 직렬화 계층, 통합 테스트
